# AI 금융 챌린지 자료

- 자세한 버전
    
    각 담당자는 기능 코드만 만드는 것이 아니라 `담당 화면·테스트·문서 반영`까지 완료해야 함.
    
    # 0. 개발 시작 전 4명이 같이 할 일
    
    8월 26일에 먼저 확정해야 함.
    
    ## 0-1. MVP 범위 확정
    
    반드시 구현할 기능은 다음으로 고정함.
    
    1. 합성 카드거래 조회
    2. 장기할부 피해 가능 거래 필터링
    3. 가맹점 폐업 상태 확인
    4. 카드사 앱 알림 시뮬레이션
    5. 소비자의 실제 서비스 중단 여부 확인
    6. 계약서·문자자료 입력
    7. OCR 및 핵심정보 추출
    8. AI의 시간순 정리·모순·누락 분석
    9. 규칙 엔진의 기본요건 확인
    10. 제출자료 초안 생성
    11. 결과 내려받기와 카드사 공식 접수 경로 안내
    
    다음 기능은 이번 MVP에서 제외함.
    
    - 실제 카드사 거래 API 연결
    - 실제 카드사 앱 제작
    - 실제 푸시·문자 발송
    - 카드사 자동 접수
    - 모든 카드사 지원
    - 실제 개인정보 사용
    - AI 파인튜닝
    - 결제 자동 취소
    - 최종 법률 판단
    
    ## 0-2. 화면 경로 확정
    
    예시는 다음과 같음.

    ```
    /case/demo-001            서비스 중단 여부 확인
    /case/demo-001/evidence   자료 입력
    /case/demo-001/analysis   AI 분석 결과
    /case/demo-001/result     기본요건 및 제출자료
    ```
    
    ## 0-3. 공통 데이터 형식 확정
    
    각자 개발을 시작하기 전에 다음 JSON 파일을 같이 만들어야 함.
    
    - `transactions.fixture.json`

    이 파일이 있어야 앞사람의 기능을 기다리지 않고 동시에 개발할 수 있음.
    
    ## 0-4. 대표 사례 확정
    
    모든 팀원이 같은 대표 사례를 사용해야 함.
    
    ```
    가맹점: 올데이 피트니스
    계약일: 2026.03.02
    결제금액: 1,200,000원
    할부기간: 12개월
    서비스 중단일: 2026.08.10
    이용기간: 약 5개월
    남은 할부기간: 7개월
    남은 할부금: 700,000원
    가맹점 상태: 폐업
    환불 요청: 문자로 요청했으나 답변이 없음
    ```
    
    실제 업체가 아닌 합성 사례임을 표시함.
    
    # A. 거래 탐지·사례 생성·규칙 엔진 담당
    
    ## A-1. 합성 카드거래 데이터 제작
    
    최소 5건을 제작함.
    
    | 거래 | 금액·결제방식 | 예상 결과 |
    | --- | --- | --- |
    | 편의점 | 35,000원 일시불 | 제외 |
    | 전자제품 | 800,000원 6개월 | 장기 서비스 업종이 아니므로 제외 |
    | 헬스장 | 1,200,000원 12개월 | 확인 대상 |
    | 학원 | 900,000원 6개월 | 남은 할부금이 없어 제외 |
    | 피트니스 | 600,000원 6개월 | 정상 영업이므로 알림 미발송 |
    
    각 거래에 다음 정보가 포함되어야 함.
    
    ```
    거래 ID
    가맹점명
    가맹점 업종
    결제금액
    결제일
    최초 할부 개월 수
    납부한 개월 수
    남은 할부금
    사업자 식별값
    가맹점 영업상태
    ```
    
    ## A-2. 대상 거래 필터링 구현
    
    다음 조건을 코드로 판정함.
    
    - 결제금액 20만 원 이상
    - 최초 할부기간 3개월 이상
    - 남은 할부금 존재
    - 장기 서비스 업종
    - 가맹점 상태 확인이 필요한 거래
    
    조건별 결과도 보여줘야 함.
    
    ```
    결제금액 기준: 충족
    할부기간 기준: 충족
    잔여 할부금: 존재
    장기 서비스 업종: 해당
    최종 결과: 가맹점 상태 확인 대상
    ```
    
    ## A-3. 가맹점 상태조회 기능 구현
    
    기본 시연에서는 국세청 API 명세 형식을 반영한 합성 응답을 사용함.
    
    ```
    {
      "businessNumber": "000-00-00000",
      "statusCode": "03",
      "statusLabel": "폐업",
      "closedDate": "2026-08-10",
      "isSynthetic": true
    }
    ```
    
    결과는 다음 네 가지로 처리함.
    
    - 정상 영업
    - 휴업
    - 폐업
    - 확인 불가
    
    시간이 남으면 실제 국세청 API 연결 확인 기능을 별도로 추가할 수 있음. 대표 시연 자체는 합성 응답으로 고정함.
    
    ## A-4. 사례 생성 API 구현
    
    잠재적 피해 거래가 발견되면 사례를 생성함.
    
    ```
    POST /api/cases
    ```
    
    입력 예시는 다음과 같음.
    
    ```
    {
      "transactionId": "tx-003",
      "merchantName": "올데이 피트니스",
      "amount": 1200000,
      "installmentMonths": 12,
      "remainingBalance": 700000,
      "merchantStatus": "폐업"
    }
    ```
    
    출력 예시는 다음과 같음.
    
    ```
    {
      "caseId": "demo-001",
      "caseUrl": "/case/demo-001"
    }
    ```
    
    D가 해당 `caseUrl`을 앱 알림 화면에 연결할 수 있도록 전달함.
    
    ## A-5. 기본요건 규칙 엔진 구현
    
    다음 조건을 코드로 확인함.
    
    - 결제금액 기준 충족 여부
    - 할부기간 기준 충족 여부
    - 남은 할부금 존재 여부
    - 서비스 제공 중단 여부
    - 환불 완료 여부
    - 대체 서비스 제공 여부
    - 소비자 귀책 여부
    - 증빙자료 확보 여부
    
    판정은 다음 세 개만 사용함.
    
    - 기본요건 충족 가능성이 있음
    - 추가자료 확인이 필요함
    - 기본요건 충족이 어려움
    
    AI가 판정하는 것이 아니라 코드가 동일한 조건에 동일한 결과를 반환하게 함.
    
    ## A-6. 거래 탐지 화면 구현
    
    `/demo/detection` 화면에 다음 내용을 표시함.
    
    - 카드거래 목록
    - 각 거래의 필터링 조건
    - 제외된 이유
    - 가맹점 상태
    - 최종 알림 대상 거래
    - ‘사례 생성’ 버튼
    
    ## A-7. 테스트
    
    최소 다음을 확인함.
    
    - 일시불 거래가 제외되는지
    - 장기 서비스가 아닌 업종이 제외되는지
    - 잔여 할부금이 없으면 제외되는지
    - 정상 영업이면 알림이 생성되지 않는지
    - 폐업 장기할부 거래만 사례로 생성되는지
    - 같은 입력에 규칙 엔진이 항상 같은 결과를 반환하는지
    
    ## A-8. 문서
    
    기획서에는 다음을 작성함.
    
    - 소비자가 피해를 직접 발견해야 하는 기존 구조
    - 장기할부 서비스 폐업 피해 문제
    - 카드사가 거래데이터를 활용할 수 있는 이유
    - 소비자와 카드사가 얻는 효과
    - 다른 장기 서비스 업종으로의 확장성
    
    기능명세서에는 다음을 작성함.
    
    - MVP에 실제 구현한 기능 범위
    - 합성데이터 사용 범위
    - 실제 카드사 연동이 제외됐다는 점
    - 규칙 엔진의 판정 기준
    
    ## A 완료 기준
    
    - 탐지 화면이 실제로 작동함
    - 거래 조건을 바꾸면 결과가 달라짐
    - 사례 생성 API가 사례 URL을 반환함
    - 규칙 엔진의 테스트를 통과함
    - 화면 캡처와 테스트 방법을 문서에 남김
    
    # B. 자료 입력·OCR·정보 추출 담당
    
    ## B-1. 합성 증빙자료 제작
    
    최소 다음 자료를 제작함.
    
    1. 헬스장 이용계약서
    2. 환불을 요청한 문자 대화
    3. 서비스 중단 안내문 또는 이용 기록
    
    자료에는 대표 사례와 같은 정보가 들어가야 함.
    
    ```
    계약일: 2026.03.02
    계약금액: 1,200,000원
    계약기간: 12개월
    환불 요청일: 2026.08.11
    서비스 중단일: 2026.08.10
    ```
    
    실제 상호·전화번호·주소·사업자번호는 사용하지 않음.
    
    ## B-2. 자료 입력 화면 구현
    
    `/case/demo-001/evidence` 화면에 다음 기능을 구현함.
    
    - 예시문서 선택
    - 이미지 또는 PDF 업로드
    - 문자 내용 직접 입력
    - 업로드된 자료 목록 표시
    - 자료 삭제와 재업로드
    - 파일 크기와 형식 확인
    - 개인정보 안내문 표시
    
    ## B-3. OCR 연결
    
    OCR 결과로 문서의 전체 텍스트를 얻음.
    
    처리 흐름은 다음과 같음.
    
    ```
    파일 업로드
    → 파일 형식 확인
    → OCR 호출
    → 텍스트 추출
    → 핵심 항목 구조화
    ```
    
    OCR 실패 시 다음을 표시함.
    
    - 인식 실패 안내
    - 다시 업로드
    - 직접 입력
    - 예비 합성 결과 사용
    
    대표 시연은 OCR API 오류가 발생해도 계속 진행될 수 있어야 함.
    
    ## B-4. 핵심정보 추출
    
    OCR 텍스트에서 다음 정보를 구조화함.
    
    ```
    {
      "contractDate": "2026-03-02",
      "contractAmount": 1200000,
      "serviceStartDate": "2026-03-02",
      "serviceEndDate": "2027-03-01",
      "refundRequestDate": "2026-08-11",
      "serviceStopDate": "2026-08-10",
      "replacementServiceOffered": null,
      "sourceDocuments": []
    }
    ```
    
    값이 확인되지 않으면 임의로 채우지 않고 `null` 또는 `미확인`으로 저장함.
    
    ## B-5. 문서별 출처 표시
    
    추출한 정보가 어떤 문서에서 나왔는지 기록함.
    
    예시는 다음과 같음.
    
    ```
    계약금액 1,200,000원
    → 출처: 이용계약서
    
    환불 요청일 2026.08.11
    → 출처: 문자 대화
    
    서비스 중단일 2026.08.10
    → 출처: 폐업 안내문
    ```
    
    C가 사실과 주장을 구분할 수 있도록 출처를 같이 전달함.
    
    ## B-6. 개인정보 처리 표시
    
    화면에 다음 내용을 명시함.
    
    - 공모전 시연에서는 합성문서 사용
    - 실제 개인정보가 포함된 문서는 업로드하지 않도록 안내
    - 파일을 장기간 보관하지 않음
    - 카드번호·주민등록번호는 수집하지 않음
    
    ## B-7. 테스트
    
    최소 다음을 확인함.
    
    - 샘플 이미지가 업로드되는지
    - PDF가 업로드되는지
    - 파일 크기 제한이 작동하는지
    - OCR 결과가 화면에 표시되는지
    - 정보가 없는 경우 `미확인`으로 처리되는지
    - OCR 실패 시 예비 결과로 넘어가는지
    - 문서를 삭제하고 다시 분석할 수 있는지
    
    ## B-8. 문서
    
    기획서에는 다음을 작성함.
    
    - 사용하는 데이터 종류
    - 합성 카드거래와 합성 증빙자료
    - 국세청 API 명세 기반 응답
    - OCR과 LLM의 역할
    - 개인정보 최소수집
    - 실제 도입 시 카드사 내부 처리 구조
    
    기능명세서에는 다음을 작성함.
    
    - AI 입력 데이터
    - OCR 결과
    - 구조화된 출력 데이터
    - 개인정보 포함 여부
    - 파일 제한
    - 오류 처리 방식
    
    ## B 완료 기준
    
    - 샘플 계약서와 문자가 실제로 입력됨
    - OCR 결과가 표시됨
    - 주요 정보가 JSON으로 생성됨
    - 정보의 문서 출처가 포함됨
    - OCR 실패 상태에서도 다음 단계로 이동할 수 있음
    
    # C. AI 분석·제출자료 내용 담당
    
    ## C-1. AI 입력 형식 정의
    
    B가 전달한 자료를 다음 구조로 입력받음.
    
    ```
    {
      "case": {},
      "documents": [],
      "extractedFields": {},
      "rawTexts": []
    }
    ```
    
    AI에 전체 개인정보를 넘기지 않고 분석에 필요한 정보만 전달함.
    
    ## C-2. AI 분석 출력 형식 정의
    
    AI가 반드시 다음 JSON 형식으로 반환하도록 함.
    
    ```
    {
      "timeline": [],
      "confirmedFacts": [],
      "userClaims": [],
      "unresolvedItems": [],
      "contradictions": [],
      "missingEvidence": [],
      "followUpQuestions": [],
      "submissionSummary": ""
    }
    ```
    
    자유로운 장문만 반환하지 않도록 구조화 출력이나 JSON 검증을 적용함.
    
    ## C-3. 시간순 관계 분석
    
    AI가 자료를 다음과 같이 정리하게 함.
    
    ```
    2026.03.02 계약 및 결제
    → 2026.08.10 서비스 중단
    → 2026.08.11 소비자 환불 요청
    → 2026.08.13 가맹점 답변 없음
    ```
    
    날짜를 확인할 수 없으면 확정된 날짜처럼 표현하지 않음.
    
    ## C-4. 사실·주장·미확인 사항 구분
    
    예시는 다음과 같음.
    
    ### 확인된 사실
    
    - 계약서상 결제금액은 120만 원임
    - 카드거래상 12개월 할부임
    - 문자에서 환불을 요청한 기록이 확인됨
    
    ### 소비자 주장
    
    - 더 이상 시설을 이용하지 못하고 있음
    - 가맹점이 답변하지 않았다고 설명함
    
    ### 미확인 사항
    
    - 다른 지점 이용 가능 여부
    - 환불 처리 여부
    - 계약 양도 또는 대체 서비스 여부
    
    ## C-5. 모순 탐지
    
    다음과 같은 모순을 탐지함.
    
    - 계약서의 계약기간과 사용자가 입력한 기간이 다름
    - 환불 완료라고 적혀 있지만 카드취소 내역이 없음
    - 다른 지점 이용이 가능하다는 안내와 소비자 진술이 다름
    - 남은 이용기간 계산이 자료마다 다름
    
    모순이 없으면 억지로 만들어내지 않고 `확인된 모순 없음`으로 표시함.
    
    ## C-6. 부족한 증빙 탐지
    
    다음 자료가 있는지 확인함.
    
    - 계약서
    - 카드 결제내역
    - 환불 요청 기록
    - 서비스 중단 정황
    - 남은 이용기간
    - 대체 서비스 제공 여부
    
    부족한 자료가 있으면 카드사 제출 전에 무엇을 추가해야 하는지 안내함.
    
    ## C-7. 추가 질문 생성
    
    모든 사용자에게 같은 질문을 제시하지 않고 자료에 따라 질문을 생성함.
    
    예시는 다음과 같음.
    
    - 다른 지점에서 이용할 수 있다는 안내를 받았는지
    - 가맹점에 환불을 요청한 날짜가 언제인지
    - 환불이 실제 카드취소 내역에 반영됐는지
    - 계약서상 대체 서비스 조항이 있는지
    
    ## C-8. 제출자료 초안 내용 생성
    
    다음 항목을 생성함.
    
    - 거래정보
    - 계약내용
    - 서비스 중단 경위
    - 환불 요청 경위
    - 남은 이용기간과 할부금
    - 첨부자료 목록
    - 미확인 사항
    - 소비자가 확인해야 할 내용
    
    AI가 다음과 같이 단정하지 않도록 함.
    
    - “환불받을 수 있음”
    - “할부항변권이 인정됨”
    - “카드사가 반드시 취소해야 함”
    
    대신 다음처럼 표현함.
    
    - “기본요건 확인이 필요한 사례임”
    - “최종 인정 여부는 카드사가 심사함”
    - “추가자료 제출이 필요할 수 있음”
    
    ## C-9. AI 분석 화면 구현
    
    `/case/demo-001/analysis` 화면에 다음을 표시함.
    
    - 시간순 정리
    - 확인된 사실
    - 소비자 주장
    - 미확인 사항
    - 자료 간 모순
    - 부족한 증빙
    - 추가 질문
    - 제출자료 초안 요약
    
    ## C-10. 테스트
    
    최소 다음 사례를 테스트함.
    
    1. 자료가 충분한 사례
    2. 환불 요청 기록이 없는 사례
    3. 이미 환불받은 사례
    4. 다른 지점 이용이 가능한 사례
    5. 계약서와 사용자 입력이 모순되는 사례
    6. 결제금액이나 할부기간 기준을 충족하지 않는 사례
    
    각 사례에서 AI가 사실을 새로 만들어내지 않는지 확인함.
    
    ## C-11. 문서
    
    기획서에는 다음을 작성함.
    
    - 서비스 전체 핵심내용
    - 기존 카드사 접수 서비스와의 차이
    - AI가 필요한 이유
    - AI와 규칙 엔진의 역할 구분
    - AI가 최종 법적 결정을 하지 않는 구조
    
    기능명세서에는 실제 동작하는 기능을 표로 정리함.
    
    - 기능명
    - 기능 설명
    - 관련 화면
    - 입력값
    - 출력값
    - 구현 상태
    
    ## C 완료 기준
    
    - AI가 정해진 JSON 구조로 결과를 반환함
    - 시간순 정리와 사실 구분이 작동함

    - 입력자료에 없는 사실을 단정하지 않음

    - AI 오류 시 예비 분석 결과로 넘어갈 수 있음

    # 4명이 공통으로 해야 하는 일
    
    ## 1. 코드 교차 검토
    
    - A 기능은 D가 확인함
    - D 기능은 A가 확인함
    - B 기능은 C가 확인함
    - C 기능은 B가 확인함
    
    B와 C는 OCR→AI 분석 연결을 확인하고, A와 D는 탐지→알림→결과 연결을 확인함.
    
    ## 2. 시나리오 공동 검증
    
    최소 세 가지 시나리오를 전원이 직접 실행함.
    
    ### 시나리오 1. 기본요건 충족 가능
    
    폐업·잔여 할부금·환불 요청 기록이 모두 존재함.
    
    ### 시나리오 2. 추가자료 필요
    
    폐업과 잔여 할부금은 확인되지만 환불 요청 기록이 없음.
    
    ### 시나리오 3. 대상 가능성 낮음
    
    이미 환불받았거나 다른 지점에서 정상 이용 중임.
    
    ## 3. 두 문서 공동 검토
    
    전원이 다음을 확인함.
    
    - 두 문서의 서비스명이 같은지
    - 기능 수와 기능명이 같은지
    - 문서에 적힌 기능이 실제 배포 URL에서 작동하는지
    - 미구현 기능을 구현한 것처럼 쓰지 않았는지
    - AI의 역할을 과장하지 않았는지
    - 합성데이터 사용 사실이 명확한지
    - 최종 결정 주체가 카드사라고 적혀 있는지
    - 모든 출처가 정상적으로 열리는지
    
    # 기능 하나의 완료 기준
    
    각자 “코드 작성 완료”만으로 끝내지 않고 다음 조건을 모두 충족해야 완료로 처리함.
    
    - 기능이 실제로 실행됨
    - 담당 화면이 존재함
    - 정상 입력 테스트를 통과함
    - 오류 입력 테스트를 통과함
    - 다른 기능과 연결됨
    - 다른 팀원이 직접 실행해봄
    - 화면 캡처를 저장함
    - 기능명세서에 반영함
    - 제한사항을 기록함
    
    이 기준으로 나누면 각자 개발·화면·테스트·문서를 모두 맡게 되므로 특정 팀원에게 마무리 업무가 몰리는 것을 방지할 수 있음.
