# A 담당 구현 지침

> 이 문서는 금융 AI Challenge의 A 담당 범위와 현재 `nodown` 저장소에서의 완료 기준을 고정하기 위한 작업 지침이다.

## 1. A의 최종 책임 범위

A는 다음 흐름을 코드·화면·테스트까지 완료한다.

```text
합성 카드거래 조회
→ 장기할부 피해 가능 거래 필터링
→ 가맹점 상태 모의조회
→ 폐업 거래 사례 생성
→ 할부항변 기본요건 규칙 판정
→ 거래 탐지 화면에서 근거 표시
```

담당 파일은 다음과 같다.

| 영역 | 파일 |
| --- | --- |
| 거래·사례 데이터 | `data/transactions.json`, `data/demo_cases.json` |
| 거래 탐지·상태조회·사례 API | `routes/detection.py`, `services/case_service.py` |
| 규칙 엔진 | `services/rule_service.py` |
| 탐지 화면 | `templates/detection.html`, `static/js/detection.js` |
| 테스트 | `tests/test_case_service.py`, `tests/test_rule_service.py`, `tests/test_detection.py` |

`app.py`, `requirements.txt`, B·C 담당 서비스는 상의 없이 변경하지 않는다. 공통 레이아웃과 최종 결과 화면은 D가 통합한다.

## 2. MVP 판정 기준

거래 탐지의 기본 조건은 다음과 같다.

- 결제금액이 200,000원 이상
- 최초 할부기간이 3개월 이상
- 남은 할부금이 존재
- 장기 서비스 업종
- 가맹점 상태를 모의조회한 결과가 `폐업`이면 알림 대상

정상 영업 거래는 알림을 만들지 않는다. 휴업·확인 불가 거래는 “상태 추가 확인”으로 표시하되, 대표 시연의 사례 생성 대상은 폐업 거래로 고정한다.

모든 상태조회 결과는 합성 데이터임을 표시한다. 실제 카드사 거래 API와 실제 국세청 API 연결은 이번 MVP 범위가 아니다.

## 3. 규칙 엔진 판정 기준

`services/rule_service.py`는 점수나 확률을 만들지 않고 조건의 상태만 평가한다. 출력 verdict는 다음 세 가지 중 하나만 사용한다.

1. `기본요건 충족 가능성 있음`
2. `추가자료 확인 필요`
3. `기본요건 충족 어려움`

대표 사례의 판정에 사용하는 조건은 다음과 같다.

- 가맹점 폐업 여부
- 남은 할부금 존재 여부
- 서비스 중단 후 미이용 여부
- 결제금액·할부기간 기준
- 환불 미완료 여부
- 대체 서비스 미제공 여부
- 소비자 귀책 없음
- 증빙자료 확보 여부

자료가 `None`이면 임의로 충족 처리하지 않고 `추가자료 확인 필요`로 판정한다. 화면에는 조건별 `충족`, `미충족`, `추가 확인 필요`와 판정 근거를 함께 표시한다. 최종 인정 여부는 카드사가 결정한다.

## 4. API 계약

### 가맹점 상태 모의조회

```text
GET /api/merchant-status/<transaction_id>
```

응답 예시:

```json
{
  "businessNumber": "000-00-00003",
  "statusCode": "03",
  "status": "closed",
  "statusLabel": "폐업",
  "closedDate": "2026-08-10",
  "isSynthetic": true
}
```

### 사례 생성

```text
POST /api/cases
Content-Type: application/json
```

요청:

```json
{
  "transactionId": "TX-1003"
}
```

응답:

```json
{
  "caseId": "CASE-001",
  "caseUrl": "/detection/CASE-001",
  "isSynthetic": true
}
```

사례 생성은 알림 대상 거래에서만 성공한다. 정상 영업·기준 미달 거래는 HTTP 400과 제외 사유를 반환한다.

## 6. A 완료 체크리스트

- [x] 합성 거래가 12건이다.
- [x] 거래마다 금액·업종·할부·잔여금·사업자 식별값·영업상태가 있다.
- [x] 필터 조건별 결과와 제외 사유가 화면에 보인다.
- [x] 상태조회 결과가 정상 영업·휴업·폐업·확인 불가를 구분한다.
- [x] 폐업 장기할부 거래만 사례 생성 API를 통해 `caseId`와 `caseUrl`을 받는다.
- [x] 규칙 엔진이 같은 입력에 항상 같은 결과를 반환한다.
- [x] `None`인 정보는 추가자료 확인으로 처리된다.
- [x] 정상 영업 거래는 사례가 생성되지 않는다.
- [x] 테스트가 통과한다.
- [ ] 대표 화면을 팀원 한 명이 직접 실행했다.
- [x] 합성 데이터와 최종 판단 주체가 화면에 표시된다.

## 7. 팀원에게 넘길 때 같이 전달할 것

```text
대표 거래: TX-1003
대표 사례: CASE-001
탐지 화면: /detection/
사례 상세: /detection/CASE-001
상태조회 API: GET /api/merchant-status/TX-1003
사례 생성 API: POST /api/cases {"transactionId":"TX-1003"}
```

다음 담당자는 A의 내부 필드명을 임의로 바꾸지 않는다. 변경이 필요하면 `case_id`, `transaction_id`, `merchant_status`, `remaining_balance`를 우선 유지하고 팀에 알린다.
